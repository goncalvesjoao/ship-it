# PR it

## User questions

Before asking or relaying any user question, read and follow [the user question rules](references/user-questions.md).

Requires GitHub CLI (`gh`), GitHub authentication, and Matt Pocock's `pr` skill. Accept an optional `#<gh-issue-id>` identifying the spec issue, not a PR number. Without it, use the supplied context and current branch as before.

1. Inspect repository instructions, `git status`, the current branch, and remotes. Resolve the target repository and base branch from the user's request, repository configuration, or GitHub's default branch. Check `gh auth status`. Ask only when the target is ambiguous or a prerequisite is missing.
2. When a spec issue number is supplied, resolve its repository and fetch the issue URL with `gh issue view`; use that verified URL as the report identity. Locate the supplied implementation report or find the report under `docs/implementations/` matching the authoritative spec URL. If it is absent from the current checkout, inspect existing worktrees and local branch contents, then relevant remote branches after fetching if needed. Look for `docs/implementations/<issue-number>.md` and verify its recorded spec URL. Read Git branch contents without switching or modifying unrelated worktrees. Read it for decisions, approvals, limitations, and validation evidence. Resolve ambiguous matches before editing; an expected but missing report leaves publication incomplete. PRs unrelated to an `implement-it` run need no implementation report. When recovering from a report, locate the recorded integration branch in its recorded repository and use an existing suitable checkout or safely check out that branch. Verify the report on that branch matches the spec; missing or conflicting branch identity is a blocker, not permission to publish from the current branch or create a replacement. Honor supplied constraints and preserve unrelated local work. Prepare the head branch. Without a recovered implementation branch, if on the base branch or a detached HEAD, create a descriptive branch. Review uncommitted changes and commit only files belonging to the requested work, naming paths explicitly. Preserve unrelated changes. Inspect the complete diff and commits against the base branch.
3. Check for an existing open PR for this head and base in the target repository before checks or body preparation. Retain its URL and fetch repository/head-repository identity, base, head branch and SHA, title, body, draft state, and labels. After an uncertain creation result, check again before retrying.

   Reuse validation only when verified evidence identifies the exact current `HEAD`, all required checks passed, and no task changes remain uncommitted. For work governed by `implement-it`, also require both review axes to have zero findings against the original pinned base. Use the retained implementation result or independently verifiable check/review evidence; a report without an exact matching SHA or a generic passing claim is insufficient. Honor requests for fresh validation and changes to required checks or the validation environment. When evidence is missing, stale, failed, or incomplete, run the required validation; governed work must pass the full `implement-it` review-and-fix gate against the original pinned base. Any implementation change during preparation requires that gate before publication. Report failures and identify reused evidence accurately. Run independent read-only checks concurrently when repository instructions permit and their outputs, ports, fixtures, and resources do not conflict. Preserve build-before-test dependencies, serialize suites sharing browser/server state, and avoid running a second build when a test command already builds. Await every command and retain its exit status and evidence; all required checks must pass before publication or gate completion.

   If validation is established and the existing PR's repository, base, actual head repository/branch, and SHA match the intended publication, compare its title and body with the retained final description when available, otherwise inspect them against the complete diff, spec, current user constraints, validation evidence, and `pr` template. Verify required closing references, requested draft state, and `status/ready-for-review`. If all match and no publication work remains, attach the PR in Codex when supported and return its URL, verified head SHA, report path when present, and validation summary without regenerating the body, rerunning checks, pushing, or editing the PR. If anything differs or cannot be verified, continue with the existing PR and repair only pending work; reuse its correct description when only labels or attachment remain.
4. When the description needs preparation or revision, invoke the installed `pr` skill to write the body using the complete PR diff, user context, and actual validation results. If it is not in the skill catalog, locate and read its `SKILL.md` in the available skills folder. If missing, ask the user to install it. Keep its template and guidance authoritative. Supply honest evidence: when no before run exists, say so; never invent screenshots or passing tests. Write a concise title describing the resulting change.
5. Save the generated body verbatim to a temporary Markdown file. Push the head branch to the intended remote with `git push --set-upstream <remote> <head>` if needed. Use a normal push; resolve rejected pushes without force-pushing. For an existing PR, compare its title and body with the prepared final description and update changed values with `gh pr edit <pr-number> --repo <owner/repo> --title <title> --body-file <body-file>`. Preserve its other metadata and draft state unless the user explicitly requested a draft-state change; apply and verify that change through the supported GitHub mechanism. Otherwise, create the PR with explicit values:

   ```sh
   gh pr create --repo <owner/repo> --base <base> --head <head> --title <title> --body-file <body-file>
   ```

   Quote argument values safely. For a fork, use `<owner>:<head>` for `--head`. Add `--draft` when requested. Opening the PR authorizes the commits and push needed for the requested work; proceed without an extra confirmation. Let the generated body supply the description rather than `--fill`.
6. For a new or reused PR, ensure `status/ready-for-review` exists in the target repository. Create it if missing with `gh label create 'status/ready-for-review' --repo <owner/repo>`, preserving existing label settings. Apply it with `gh pr edit <pr-number> --repo <owner/repo> --add-label 'status/ready-for-review'`. Verify the PR's URL, base, head branch and SHA, intended title and body, and label with `gh pr view --repo <owner/repo> <pr-number> --json url,baseRefName,headRefName,headRefOid,title,body,labels`. Report labeling failures as incomplete work. In Codex, attach it with `attach_artifact` when available. Remove the temporary body file after success and return the PR URL, final verified head SHA, implementation report path when present, and a brief validation summary. If blocked, report the exact blocker and preserve the prepared body for retry.
